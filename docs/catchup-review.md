# 回放 / 时移审查记录

审查日期：2026-10-24。基准：`test` 分支 `638e10f`。以下为本次确认并修复的问题，
不是对所有频道、所有保留期或电视端播放器的完整认证。

## 主要发现

| 级别 | 原实现位置 | 问题与影响 | 本次处理 |
|---|---|---|---|
| P1 | `catchup_server.py:parse_ts` | `mktime()` 已使用宿主机时区，再减 8 小时，部署到北京时间机器会重复偏移 | 显式 `UTC+08:00` 日期解析；UTC、上海、纽约环境回归测试 |
| P1 | `catchup_server.py:seg_url` | 目录桶固定为 `HH30`，上半小时片段错误寻址 | 按 UTC 分钟选择 `HH00` / `HH30`；保留源站实际路径前缀、轨道和查询参数 |
| P1 | `catchup_server.py:resolve_range` | 每 12 段抽样不能保证其余片段可用；多次漂移搜索可能阻塞很久 | 生成列表只验证首段，后续 TS 按需小范围 GET 验证并解析漂移；限制单请求预算与并发 |
| P1 | `catchup_server.py:build_playlist` | 所有请求固定 `VOD` + `ENDLIST`，正在播出的节目和时移不会继续更新 | 已结束节目输出 VOD；正在播出节目及独立时移接口输出可刷新 HLS |
| P2 | 时移持续刷新 | 若按 URL 最初的起播时间校验保留期，长时间播放最终会被错误拒绝 | 时移校验当前最多 4 小时滚动窗口；覆盖原始起点已过期后继续刷新的回归测试 |
| P1 | `sync-iptv.yml` / 两个新增列表 | 自动任务只维护直播列表，回放列表与源站频道 ID 会逐渐脱节 | 配置驱动生成回放/直连列表，自动任务生成、测试后一起提交；服务自动刷新频道名单 |
| P2 | `catchup_server.py:Handler.do_GET` | 空播放列表本身有 7 行，但用 `<=6` 判空，实际仍返回 200 | 无法解析起始片段时明确返回 404，不生成伪成功 HLS |
| P2 | `catchup_server.py:Handler.do_GET` | `b<=a` 一律当时长，倒置日期可能被误当超大时长；未来请求被改写到过去 | 严格校验日期、正向区间、4 小时上限和直播边缘；只对合理的小整数保留时长兼容 |
| P2 | `catchup_server.py:resolve_range` | 起点回推向上取整，丢失节目开头最多 9 秒；硬跳过 30 秒也会静默丢内容 | 从包含起点的完整片段开始，`EXT-X-START` 给出精确偏移；缺失片段明确失败 |
| P2 | `catchup_server.py:probe` | 只认 HTTP 200/206，HTML 错误页也可能被当成有效片段 | `Range: bytes=0-187` 请求并验证 TS 同步字节；区分 404/410 与上游异常 |
| P2 | 脚本模块顶层 / `/status` | 导入模块会解析进程参数；状态接口返回 Python `repr` 而非 JSON | 参数解析移到 `main()`；健康检查返回 JSON，补齐 HEAD 和禁缓存响应 |

此外修复同步脚本两处边界问题：新增频道选取第一条**可识别频道 ID**的模板 URL；
无其他属性的 `EXTINF` 添加频道号时不再把频道号写到频道名后面。

## 验证

- 标准库 `unittest` 离线测试；包含真实本地 HTTP 服务的状态码、HEAD、跳转和繁忙处理，
  不需要运营商网络、外部 Python 包或电视客户端。
- 使用已有内网代理对比测试：同一个上半小时历史 TS，正确 `HH00` 目录返回 206，
  原先固定 `HH30` 路径返回 404；媒体首字节为 MPEG-TS 同步字节 `0x47`。
- 通过临时本地回放服务请求 CCTV1 约 1 小时前的短回放、约 3 分钟前的时移及正在播出区间，
  验证 HLS 首尾片段经服务跳转后均能取到 TS；回放带 `ENDLIST`，另外两种不带。
- 用 `ffprobe` 读取新服务返回的真实回放 HLS，成功识别 1920×1080 HEVC 视频和 AAC 音频，
  退出码为 0；这不是完整节目的逐帧解码验收。

## 尚存边界

- 历史片段不是公开稳定的回放 API，依赖“时间戳 + 序号大致线性”的源站实现。
  程序仍保留 test 分支的锚点相位回推，不回退到错误的绝对 10 秒网格。
- 频道保留窗口继承 test 分支探测结果，不代表本次验证了 79 个频道所有日期。
- 频道重启、真实缺失片段、时间戳相位变化、源站限流可能导致失败；只做有限序号漂移搜索，
  不无限探测，也不把错误伪装成空回放成功。
- 客户端必须支持 HLS 相对片段地址和 HTTP 跳转，并能访问原直播代理；未在真实酷9/TVBox
  电视端做按键交互验收。默认占位符来自 test 分支的酷9兼容修复，不保证所有播放器通用。
- 本服务无认证、不录制节目、不转发 TS 内容，必须限制在可信内网。时移接口不等于播放器
  自动出现暂停/拖动按钮；已结束节目的片段边界可能多带最多 9 秒尾部媒体。

## 2026-10-29 长播放修复

本轮修改仅在本机进行离线验证，没有更新路由器、重启服务或操控电视。保留日志不足以
确定酷9此前卡顿的实际原因；以下修复针对代码及模拟源中能够确认的问题。

| 问题 | 修复及验证 |
|---|---|
| 漂移搜索遗漏 `±2..5`，后续每片重复从零搜索 | 小偏移改为连续搜索；按频道和媒体时间缓存真实序号，仅用同一片或相邻片预测并重新校验。模拟前 120 秒正常、随后 `+2` / `+60` 漂移，边界处恢复后后续分片只需一次探测。远处拖动、另一频道、提示过期或新断点不会直接复用错误偏移。 |
| 忽略上游时间线断点 | 保留可观测断点及序号/时间跳变，在生成 HLS 时输出 `EXT-X-DISCONTINUITY` 和独立维护的 `EXT-X-DISCONTINUITY-SEQUENCE`。窗口滑动、上游标记离开直播列表、重复观测及元数据上限均有测试。不会为了“容错”每 10 秒强制重置一次解码器。 |
| socket 超时不能约束持续慢传输 | 新增 `upstream.py`，同一次解析的 DNS、连接、TLS、响应头、响应体和跳转共享截止时间；截止时对活动套接字执行 shutdown，唤醒阻塞读取。DNS 使用有上限、同主机合并的后台查询；超时不占住 HTTP 处理名额，也不无限堆积任务。保留 HTTPS 证书校验。 |
| `EXT-X-START` 属性使用冒号 | 修正为 `TIME-OFFSET=...`，使用属性解析断言测试，而非继续断言错误的字符串。 |
| 过期缓存仍占用状态计数 | 地址和序号缓存按有效期清理，并继续保留容量限制；`/status` 另列有效序号提示和已观测断点数量。 |

本轮离线验收：Python 3.11.15 和 3.14.4 分别通过 83 项测试；导出的 OpenWrt 源码包
通过 63 项包内测试，`SOURCE.json` 中 20 个文件的哈希全部匹配。另检查了 Python 3.10

### 仍然需要实际源站信息的情况

- 断点记录仅来自请求时读到的直播列表，服务不会后台录制或连续扫描所有频道。
  如果历史节目中的 PTS 重置发生在观察范围之外，仅凭文件名、首字节及一个直播锚点
  无法还原它的位置。完整解决需要源站历史 HLS 索引或进一步分析媒体，不能宣称本次已覆盖。
- 文件名的时间戳相位在区间中发生改变时，原先的固定相位外推不能保证寻址正确。
  已观测断点若不在当前生成列表的 10 秒网格上，会明确返回 502，而不是静默丢弃标记；
  这不等于已经能够重建相位变化前后的全部历史时间线。
- 大范围、未知模式的序号重置仍只做有限搜索，缺失媒体仍返回错误。新增缓存不等于
  媒体已经完整下载成功，302 也不能证明电视已经收到整个 TS。
- 本机慢上游和模拟播放验证不代替真实电视长时间验收；当前版本尚未部署，勿在观看中升级。

### rtp2httpd 是否有帮助

依据 [stackia/rtp2httpd](https://github.com/stackia/rtp2httpd) 的文档及源码评估，
查阅版本为 `0944b7870349c501e250e18b1e67b0c82f4a284c`；没有安装或接入当前播放链路。

- **可以作为转发网关候选**：除了 RTP/UDP 和 RTSP，它也支持 HTTP HLS 反向代理，
  可以改写播放列表地址及 HTTP 跳转。当前 `gx.m3u` 是 HTTP HLS，不是组播源。
  HTTP 转发源码在下游发送队列接近上限时暂停读取上游，避免通过丢弃媒体字节处理慢客户端；
  这值得后续对照测试，但不能证明当前卡顿来自转发队列，也不是无上限缓冲。
- **有助于保留排障信息**：状态页提供客户端、带宽及传输量；访问日志可以关联客户端和
  上游 URL，但默认关闭，需另行启用和轮转。文档列出的访问日志字段不含逐片下载耗时，
  不能仅靠它确认电视已完整下载或解码媒体。
- **不能替代当前历史索引逻辑**：它透传/调整回放时间参数，前提是上游已有对应的回放能力；
  不会推算广西移动的历史 TS 文件名、搜索序号漂移或恢复缺失的历史 PTS 断点。
  如果以后拿到运营商可用的 RTSP 回放地址，才有条件尝试绕开这里的文件名推算方案。
- **不能直接套用所有宣传功能**：FCC/FEC/组播重排不直接作用于目前这条 HTTP HLS 源；
  FCC 还需要运营商服务器。查阅版本的媒体反向代理仅支持 HTTP 上游，不支持 HTTPS；
  能下载 HTTPS 外部 M3U 不代表能代理 HTTPS 媒体。
- **不要现在直接换源或叠加代理**：先在用户空闲时用独立端口、同频道同时间段做 A/B 测试。
  初次对照应保留现有酷9订阅及路径型时间占位符，不假定自动 M3U 重写与所有酷9格式兼容；
  当前直播网关及回放服务均保持不动。

## 2026-10-30 请求诊断与响应边界

本轮继续补足“出现卡顿时缺少可关联信息”的排障缺口，不修改历史 TS 寻址和直播订阅地址，
也没有访问真实源站、部署路由器、重启现有服务或操作电视。

| 改动 | 边界与验证 |
| --- | --- |
| 新增请求诊断 | `/status` 保留旧字段，增加完成请求、处理中请求、响应码、耗时、上游访问、探测、缓存及纠偏统计。最近失败和慢请求各最多 20 条，快照与内部数据隔离，并发更新有锁保护。 |
| 可关联的脱敏日志 | GET / HEAD 响应附带服务端生成的 `X-Request-ID`，连接复用时不重复使用；默认只记录失败及耗时至少 2 秒的请求。JSON 日志不包含原始请求路径、查询参数、客户端 IP、请求头、上游 URL 或任意异常文本。频道和节目时间仍有观看隐私。 |
| 修复客户端写超时处理 | 原来发送响应也在上游异常处理块中，写入失败可能被当成上游错误并尝试发送第二次响应。现在先释放解析名额，再发送响应；断连/写超时记录为客户端写入失败，不再次发送。 |
| 区分连接失败和超时 | 非超时的 `URLError` 改为 502；真正的超时仍为 504。日志保留固定错误类别及上游 HTTP 状态码，不从异常字符串猜测 DNS、TLS 或媒体阶段的根因。 |
| OpenWrt 与持续检查 | LuCI / UCI / procd 接入 `errors` / `all` / `off`，旧配置默认 `errors`。源码版本升至 `0.1.2-r1`，导出包含诊断模块及测试；CI 配置 Python 3.10 / 3.14 矩阵和独立导出包检查。 |
